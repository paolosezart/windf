--------------------------------------------------------------------------------
  ЧАСТЬ 0. ГЛАВНОЕ НЕДОРАЗУМЕНИЕ: МОДЕЛЬ НЕ КОМПИЛИРУЕТ
--------------------------------------------------------------------------------

  Это самое важное, что нужно понять до всего остального.

  Языковая модель НЕ умеет компилировать программы. Она умеет только
  генерировать текст — то есть писать код. Компиляцию (превращение кода
  в .exe, .apk или бинарник) делает НЕ модель, а отдельная программа:
  компилятор (gcc, clang, MSVC, javac, gradle и т.д.).

  Модель может:
    - написать исходный код;
    - вызвать компилятор через терминал (если у неё есть такая возможность);
    - прочитать ошибки компилятора и исправить код.

  Модель не может:
    - сама по себе "собрать" программу, если у неё нет доступа к терминалу.

  Отсюда вывод: "чтобы модель могла компилировать" означает на практике —
  нужно, чтобы у ИИ-агента был доступ к машине с компиляторами. Это
  обеспечивается двумя путями из ЧАСТИ 1.

  ВАЖНО ПО ТЕРМИНАМ ДАЛЬШЕ:
    "Готовый софт" = скомпилированный исполняемый файл (.exe, .apk, бинарник).
    "Модель"       = то, что пишет код.
    "Агент"        = модель + инструменты (терминал, редактор файлов).
    "CI"           = внешняя служба сборки (например GitHub Actions).


--------------------------------------------------------------------------------
  ЧАСТЬ 1. КАК ВООБЩЕ ПОЛУЧАЕТСЯ ГОТОВЫЙ СОФТ (ДВА ПУТИ)
--------------------------------------------------------------------------------

  ПУТЬ А. Сборка прямо в среде агента (локально или в песочнице OpenHands).
  ------------------------------------------------------------------------

  Агент работает в Linux-песочнице и имеет терминал. Значит, он может
  сам запускать компилятор и получать результат.

  Что это даёт:
    - Linux x86_64 — собирается нативно, без проблем.
    - Windows .exe — через кросс-компиляцию (MinGW-w64, mingw).
    - Linux ARM64 — через кросс-компиляцию (gcc-aarch64-linux-gnu).
    - Android .apk — сложнее, требует Android SDK/NDK, обычно тяжело.

  Плюс: быстро, всё в одном месте.
  Минус: не всякая среда имеет нужные компиляторы; Android и Windows
         собирать в песочнице капризно.

  ПУТЬ Б. Сборка на внешней службе (GitHub Actions). РЕКОМЕНДУЕТСЯ.
  ------------------------------------------------------------------------

  Агент пишет код и кладёт его в репозиторий GitHub. Специальный файл
  (workflow) говорит GitHub: "собери это на своих серверах под такие-то
  платформы". GitHub собирает и отдаёт готовые файлы (артефакты/релизы).

  Почему это лучший путь для вас:
    - GitHub даёт бесплатные серверы. Для ПУБЛИЧНЫХ репозиториев —
      бесплатно и БЕЗ ЛИМИТА минут (стандартные раннеры).
    - Есть готовые серверы под каждую нужную платформу (см. ЧАСТЬ 5).
    - Ваше слабое железо вообще не участвует в сборке.
    - На выходе — готовый файл, который просто скачивается.

  Минус: нужно один раз настроить workflow-файл (я помогу).

  ВЫВОД: компилировать будет GitHub Actions, а модель — писать код.
  Ваш компьютер при этом почти не напрягается.

  вы упираетесь в лимит одного — переключаетесь на другого. В сумме это
  десятки тысяч бесплатных запросов в день. Именно так и надо делать.


--------------------------------------------------------------------------------
  ЧАСТЬ 3. МОЩНОСТЬ МОДЕЛЕЙ, КОНТЕКСТ, ВЕРОЯТНОСТЬ ОШИБОК
--------------------------------------------------------------------------------

  Как читать таблицу:

    Мощность — условная оценка для написания кода (5 = отлично, 1 = слабо).
    Контекст — сколько текста модель "держит в голове" за раз (в токенах).
               1 млн токенов ≈ целая большая кодовая база.
    Ошибки   — насколько часто модель ломает код или выдумывает несуществующее.
               Чем ниже, тем лучше. "Выдумывание" = галлюцинации.

  ---

  МОДЕЛЬ                 Мощность  Контекст   Ошибки      Где взять
  ---------------------  --------  ---------  ----------  ------------------
  DeepSeek V4 Flash      5         до 1 млн   низкие      NVIDIA, OpenRouter
  Qwen3 Coder (большие)  5         до 1 млн   низкие      NVIDIA, OpenRouter
  GLM-5.x / GLM Flash    5         200K-1M    низкие      Z.ai, NVIDIA
  Kimi K2/K3             5         до 1 млн   низкие      Groq, NVIDIA
  Gemini Flash/Pro       4-5       до 1 млн   низкие      Google AI Studio
  gpt-oss-120b           4         131K       средние     Groq, Cerebras
  Llama 3.3 70B          3         128K       средние     Groq, NVIDIA
  Мелкие (3B-8B)         1-2       32K-128K   высокие     локально, Groq

  ПОЯСНЕНИЯ ПО КАЖДОМУ ПУНКТУ:

  DeepSeek V4 Flash
    Это та самая модель, на которой вы работаете сейчас бесплатно.
    Очень сильна в коде, контекст огромный (до 1 млн токенов).
    Ошибки редкие. Идеальна для агентной работы.

  Qwen3 Coder
    Семейство моделей, заточенных именно под программирование.
    Большие версии — одни из лучших открытых моделей для кода.

  GLM (Z.ai)
    Сильные китайские модели. Flash-версии бесплатны. Хорошо пишут код.

  Kimi (Moonshot)
    Отличная для фронтенда и агентных задач. Большой контекст.

  Gemini Flash/Pro
    Сильные, но помните: бесплатный тир обучается на ваших данных.
    Для учебных утилит — нормально.

  gpt-oss-120b
    Открытая модель от OpenAI. Хорошая, но чуть слабее топов.

  Llama 3.3 70B
    Уже стареющая. Работает, но код даёт менее аккуратный.

  Мелкие модели (3B-8B)
    Это ваш локальный Ollama. Годятся для мелких задач и обучения,
    но для сложной сборки софта будут часто ошибаться.

  ---

  ЧТО ЗНАЧИТ "КОНТЕКСТ" ДЛЯ ПРАКТИКИ:
    - 32K   — маленький файл, одна функция. Мелкая модель запутается.
    - 128K  — несколько файлов. Разумный минимум для реальной работы.
    - 200K+ — целый проект целиком. Комфортно.
    - 1M    — вся кодовая база с историей. Максимум.

  ЧТО ЗНАЧИТ "ВЕРОЯТНОСТЬ ОШИБОК" НА ПРАКТИКЕ:
    - Низкие  — код обычно рабочий с первого раза, редко выдумывает.
    - Средние — бывают ошибки, но исправляются с одной-двух попыток.
    - Высокие — много галлюцинаций, нужно всё проверять руками.
               Это главная причина "страшной траты нервов" на слабых
               моделях и на слабом железе.


--------------------------------------------------------------------------------
  ЧАСТЬ 4. ЧТО ВАЖНО ИМЕННО ДЛЯ СБОРКИ КОДА (АГЕНТНОСТЬ)
--------------------------------------------------------------------------------

  Не всякая умная модель годится для агента. Тут есть отдельный критерий,
  который важнее "общего ума": умение ВЫЗЫВАТЬ ИНСТРУМЕНТЫ (tool calling).

  Что это значит на практике:
    Агент должен уметь:
      - запустить команду в терминале (например, компилятор);
      - прочитать вывод, включая ошибки;
      - отредактировать файл;
      - повторить попытку.
    Модель без хорошего tool calling ломает этот цикл: путает формат,
    зацикливается, не понимает ответ инструмента.

  Итог: маленькие локальные модели (3B) для агентной сборки плохо подходят.
  Для полноценной работы нужны большие модели из ЧАСТИ 3 с пометкой
  "низкие ошибки".

  Поэтому рабочая схема такая:
    - Код и сборку ведёт СИЛЬНАЯ модель (DeepSeek V4 Flash, Qwen3, GLM).
    - Слабая локальная модель — только для мелких задач и обучения.


--------------------------------------------------------------------------------
  ЧАСТЬ 5. СБОРКА ПОД WINDOWS / ANDROID / LINUX ARM64 ЧЕРЕЗ GITHUB ACTIONS
--------------------------------------------------------------------------------

  GitHub Actions — это бесплатные серверы для сборки. Для ПУБЛИЧНЫХ
  репозиториев стандартные серверы бесплатны и БЕЗ ЛИМИТА минут.

  Доступные типы серверов (значение для runs-on в workflow):

    windows-latest        — Windows x64 (основная цель).  Готовый .exe
    ubuntu-latest         — Linux x64.                   Бинарник
    ubuntu-24.04-arm      — Linux ARM64 (нативный!).      Бинарник ARM64
    ubuntu-22.04-arm      — Linux ARM64 (старая версия)
    macos-latest          — macOS (если понадобится)

  ВАЖНО:
    - Раннеры ubuntu-*-arm и windows-11-arm работают ТОЛЬКО в публичных
      репозиториях. В приватных — упадут. Для бесплатной сборки делайте
      репозиторий публичным.
    - Windows ARM64 (windows-11-arm) тоже есть и тоже бесплатен в публичных.

  ---

  КАК ЭТО ВЫГЛЯДИТ ДЛЯ КАЖДОЙ ЦЕЛИ:

  ЦЕЛЬ 1: Windows .exe  (основная)
    Самый надёжный способ — собрать НА Windows-раннере напрямую:
      runs-on: windows-latest
      (внутри — запуск компилятора или сборка через cmake/msbuild)
    Результат: готовый .exe в артефактах, скачивается одним кликом.

  ЦЕЛЬ 2: Linux ARM64  (опционально)
    Использовать нативный ARM-раннер:
      runs-on: ubuntu-24.04-arm
    Результат: нативный бинарник ARM64 без эмуляции и кросс-сборки.

  ЦЕЛЬ 3: Android .apk  (опционально)
    Собрать на ubuntu-latest с установкой Android SDK / NDK:
      runs-on: ubuntu-latest
      шаги: установить JDK, Android SDK, запустить gradle
    Результат: .apk в артефактах.
    Примечание: это самая сложная цель, нужен проект на Gradle/Java/Kotlin.

  ЦЕЛЬ 4: Всё сразу (одним запуском)
    Используется "матрица" (matrix) — один workflow собирает несколько
    платформ параллельно. Каждая платформа — своя строка, свои артефакты.

  ---

  ЧТО ТАКОЕ "АРТЕФАКТ" И "РЕЛИЗ":
    - Артефакт — временный файл сборки, хранится ~90 дней.
    - Релиз (Release) — постоянная страница с готовыми файлами, которую
      видно всем. Именно оттуда вы скачиваете готовый софт.
    Настроив один раз, вы получаете: запушил код -> через пару минут
    на странице релиза лежит готовый .exe. Ваш ПК при этом не работает.

  ---

  КАК ЭТО СВЯЗАНО С АГЕНТОМ:
    Агент (я) может:
      - написать сам код утилиты;
      - написать workflow-файл для сборки;
      - запушить всё в GitHub;
      - дождаться сборки и проверить результат;
      - если сборка упала — прочитать лог ошибки и исправить.
    То есть весь цикл "код -> компиляция -> готовый файл" замыкается
    на агента, а тяжёлую работу делает GitHub.


--------------------------------------------------------------------------------
  ЧАСТЬ 6. РЕКОМЕНДУЕМЫЙ СТЕК ПОД ВАШИ УСЛОВИЯ
--------------------------------------------------------------------------------

  Учитывая: бесплатность, слабое железо, цель "готовый софт", Windows +
  опционально Android и Linux ARM64.

  УРОВЕНЬ 1. Основной рабочий (код + сборка). Сильные модели:
    - DeepSeek V4 Flash  — сейчас бесплатно в OpenHands (пока акция)
    - Qwen3 Coder        — через NVIDIA NIM или OpenRouter
    - GLM Flash          — через Z.ai
    Эти модели ведут сложную работу: пишут код, запускают сборку,
    исправляют ошибки.

  УРОВЕНЬ 2. Резервные облачные ключи (бесплатные, возобновляемые):
    - Groq          — быстрый, честный, без обучения на данных
    - Cerebras      — 1 млн токенов/день
    - NVIDIA NIM    — много моделей, лимит скорости
    Держите 2-3 ключа и переключайтесь при упоре в лимит.

  УРОВЕНЬ 3. Локальный резерв (Ollama):
    - qwen2.5-coder:3b — мелкие задачи, обучение
    - без интернета, без лимитов, приватно

  УРОВЕНЬ 4. Сборка готового софта:
    - GitHub Actions, публичный репозиторий
    - windows-latest (основное), ubuntu-24.04-arm (ARM64), ubuntu-latest (Android)

  ---

  ПРАКТИЧЕСКИЙ ПОРЯДОК ДЕЙСТВИЙ:
    1. Пока акция DeepSeek жива — работаем на ней (как сейчас).
    2. Заводим ключ Groq и Cerebras — это ваши бесплатные "запасные".
    3. Поднимаем локальный Ollama (см. отдельный документ).
    4. Создаём публичный репозиторий на GitHub для утилит.
    5. Настраиваем один workflow, который собирает .exe (Windows).
    6. Каждая новая утилита: агент пишет код + workflow, пушит,
       GitHub собирает, вы скачиваете готовый файл.

  При таком стеке у вас ВСЕГДА есть рабочий путь, и ни один проект
  не зависает из-за окончания чьей-то акции.


--------------------------------------------------------------------------------
  ЧАСТЬ 7. КАК ПОДКЛЮЧИТЬ ОБЛАЧНЫЙ КЛЮЧ К OPENHANDS (BYOK)
--------------------------------------------------------------------------------

  BYOK = "Bring Your Own Key" = "принеси свой ключ". Вы используете
  бесплатный ключ провайдера, и OpenHands работает на нём.

  Общий принцип (одинаков для всех провайдеров):
    1. Зарегистрироваться у провайдера (например console.groq.com).
    2. Создать API-ключ в личном кабинете.
    3. В OpenHands: Settings -> LLM -> добавить модель как профиль.
    4. Выбрать провайдера, вставить base_url и ключ, сохранить.
    5. Переключиться на этот профиль командой /model в беседе.

  Адреса (base_url) основных провайдеров:
    Groq:         https://api.groq.com/openai/v1
    Cerebras:     https://api.cerebras.ai/v1
    Google:       https://generativelanguage.googleapis.com/v1beta/openai/
    OpenRouter:   https://openrouter.ai/api/v1
    NVIDIA NIM:   https://integrate.api.nvidia.com/v1

  Все они OpenAI-совместимые — значит, подключаются одинаково.
  Разобравшись с одним, добавите остальные за минуту.

  ПОДСКАЗКА: имена моделей (например gpt-oss-120b, qwen3-coder)
  берите из личного кабинета провайдера — они там указаны точно.


--------------------------------------------------------------------------------
  ЧАСТЬ 8. ПОДВОДНЫЕ КАМНИ БЕСПЛАТНЫХ ТИРОВ
--------------------------------------------------------------------------------

  8.1. Лимиты меняются без предупреждения.
       Считайте все цифры ориентиром. Всегда проверяйте перед работой.

  8.2. Сервисы иногда закрываются целиком.
       Пример: GitHub Models полностью выключили 30 июля 2026.
       Никогда не завязывайтесь на одного провайдера.

  8.3. Бесплатно часто = данные идут на обучение.
       Google Gemini (вне ЕС/UK/Швейцария) обучается на промптах.
       Для учебных утилит — ок. Для личного/чувствительного — нет.
       Groq, Cerebras, NVIDIA — не обучаются.

  8.4. Ошибки тоже считаются в лимит.
       У OpenRouter упавшие запросы тоже тратят дневную квоту.
       Делайте паузы, не бомбите запросами в цикле.

  8.5. Качество кода зависит от модели.
       Сильная модель даёт рабочий код почти сразу. Слабая — заставляет
       возиться. Это не про "везение", а про класс модели.

  8.6. Раннеры ARM работают только в публичных репозиториях.
       Если репозиторий приватный — ubuntu-24.04-arm и windows-11-arm
       упадут. Для бесплатной сборки — делайте публичный.

  8.7. Бесплатные тиры — не для продакшена.
       Для учебных и личных утилит — идеально. Для коммерческого
       продукта с пользователями — нужен платный тариф или свой сервер.

  8.8. Контекст на бесплатном тире может быть урезан.
       Иногда бесплатно дают модель с меньшим окном, чем в платном тире.
